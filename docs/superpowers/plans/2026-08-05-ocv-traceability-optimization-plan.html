OCV1 / OCV2 接口与追溯优化方案

范围收敛版 · 2026-08-05 · 面向数据准确保存与电芯追溯

方案已确认，待实施

1. 方案结论

本期只解决 OCV1、OCV2 两类业务接口及其必要的追溯展示。每类接口保留现有单条和批量路径， 不把系统改造成严格的工序状态机。数据写入必须保证批次归属、测量字段、测试时间和审计信息准确； 工序顺序只用于展示。
2业务接口：OCV1、OCV2
1000单次批量上传最大记录数
32批次号最大字符数
项目本期决定
当前值cell_barcode 保存 OCV1/OCV2 当前快照，正常电芯追溯只展示最新一次。
审计历史继续使用 ocv1_record、ocv2_record 扩展保存每次有效上传和原始报文；不新增第三套 OCV 业务接口。
数据时序按设备 testTime 判断新旧；更早的迟到数据不保存；相同时间以后接收的数据作为当前值。
过程控制允许 OCV 早于其他工序上传，不检查前置工序，不接入人工质检闸门。
接口兼容保留现有 URL 和单条/批量调用方式；批量允许有效记录保存、无效记录返回失败明细。

2. 已确认业务规则

分类确认规则实现要求
标识批次号、电芯码、Pack 码统一去除首尾空格并转换为大写。新数据写入前统一规范化；历史数据迁移时统一大写，发生冲突则暂停迁移并输出清单。
批次号全链路最大 32 个字符。数据库相关 batch_no 扩展为 NVARCHAR(32)；DTO、路由参数和文档同步。
批次存在批次不存在时提示不存在，不保存 OCV 数据。单条请求返回批次错误；批量请求将该记录列入失败明细。
电芯创建电芯码不存在时，按已存在批次创建电芯记录。仅创建必要的半成品电芯记录，不能覆盖其他工序字段。
批次归属已有电芯属于其他批次时拒绝本次上传，原批次保持不变。在事务内锁定电芯并校验，禁止静默改写 cell_barcode.batch_no。
测量字段OCV1 要求电压、内阻；OCV2 还要求 K 值。电压单位为 V，内阻为 mΩ，K 值为 mV/h。拒绝缺失、非数字、无穷大和超出允许范围的值；不截断、不夹紧。
时间只接受带时区的 ISO 8601；未来时间只要格式正确即接受。示例：2026-08-05T18:38:15+08:00。缺失或格式错误直接拒绝。
重复时间同一电芯同一工序的相同 testTime，后接收的数据作为当前值。历史记录仍按有效上传逐条保存；当前快照比较 testTime、receivedAt、id。
迟到数据比当前快照更早的 testTime 不保存。不插入审计行、不更新快照，并在批量失败明细中说明原因。
eventId每条测量记录可带独立 eventId；没有时每次上传都保存新记录。相同 ID、相同内容返回首次结果且不新增；相同 ID、内容不同返回事件冲突。
批量最多 1000 条；有效记录保存，无效记录单独返回。有失败时 HTTP 400，但响应必须包含成功和失败明细；设备只重试失败记录。
原始报文长期保存原始报文和解析后的字段。每条有效或失败记录都进入接口日志；有效记录的原始报文同时写入 OCV 审计表。
设备编号equipmentCode 可为空。为空时保存 NULL，不写入虚假默认值。
OCV2 K 值OCV2 K 值与分选 K 值分开保存。新增 cell_barcode.ocv2_k_value；本期不使用 OCV2 覆盖分选最终 k_value。
接口安全接口暂保持公开，部署依赖网络隔离。保留请求体大小、超时、失败日志和来源信息控制；本期不增加 API Key。

3. 本期范围与边界

3.1 本期包含

OCV1 OCV2 快照 审计 批次号 32 位 只读流程展示
  • 保留四条现有路径：单条和批量 OCV1、单条和批量 OCV2。
  • 修复 OCV 多行记录被批次级查询覆盖或 JSON 解析失败的问题。

  • 批次页面显示有当前 OCV 快照的电芯数量和批次电芯总数。

这些事项已经确认了目标规则，但不作为本次两个 OCV 业务接口的阻塞项，避免把接口上线扩大成全系统重构。
  • Pack 待解析关联、有效 Pack 释放和 Pack 重组历史的完整实现。
  • 分选接口异常数值夹紧逻辑的全面改造。
  • 13 个人工工序的数据模型重构。
  • 完整工序状态机和前置工序强校验。

4. 目标数据模型

4.1 数据职责

数据对象职责读取方式
cell_barcode每个电芯每个 OCV 工序的当前最新快照。普通电芯追溯、批次电芯列表。
ocv1_recordOCV1 每次有效上传的审计记录。管理员审计查询、批次当前记录兼容查询。
ocv2_recordOCV2 每次有效上传的审计记录，包含 K 值。管理员审计查询、批次当前记录兼容查询。
接口日志成功、重复、失败的原始请求和处理结果。管理员排查设备重试、参数错误和批量部分失败。

4.2 OCV 记录字段

在现有 OCV 表上增加下列兼容字段。新增字段允许 NULL，是为了保留已经存在的旧记录；新接口写入时必须满足接口校验。

字段类型OCV1OCV2说明
barcodeNVARCHAR(32)是是新记录必有；旧记录可能为 NULL。
voltageDECIMAL(12,4)是是测量电压，单位 V。
internal_resistanceDECIMAL(12,2)是是测量内阻，单位 mΩ。
k_valueDECIMAL(12,4)否是OCV2 K 值，单位 mV/h。
test_timeDATETIME2是是设备测试时间。
received_atDATETIME2是是MES 接收时间。
source_event_idNVARCHAR(64)可选可选有值时在对应 OCV 表内唯一。
payload_hashCHAR(64)是是规范化字段的 SHA-256，用于判断相同 ID 的内容是否一致。
raw_payloadNVARCHAR(MAX)是是长期保存的单条原始报文。
ocv_voltage_min/max原有类型兼容兼容新记录将测量电压同时写入两列，避免旧页面失去数据。

4.3 快照更新规则

读取对应电芯当前快照
先处理 eventId：
  相同 eventId + 相同 payloadHash：返回首次结果，不新增记录
  相同 eventId + 不同 payloadHash：拒绝，返回 OCV_EVENT_CONFLICT

如果当前快照存在：
  incoming.testTime < current.testTime：拒绝，不插入历史，不更新快照
  incoming.testTime == current.testTime：插入历史，并以本次接收值更新快照
  incoming.testTime > current.testTime：插入历史，并更新快照

如果当前快照不存在：
  插入历史，并建立当前快照

历史行和当前快照必须在同一个数据库事务中提交。设备时间未来不单独拒绝，只要满足带时区的 ISO 8601 格式和字段校验。

5. 接口契约

5.1 路径

方法路径说明
POST/api/cells/ocv1-uploadOCV1 单条上传。
POST/api/cells/ocv1-upload/bulkOCV1 批量上传，最多 1000 条。
POST/api/cells/ocv2-uploadOCV2 单条上传。
POST/api/cells/ocv2-upload/bulkOCV2 批量上传，最多 1000 条。
GET/api/admin/ocv/records管理员分页查询 OCV 审计历史。

5.2 请求字段

字段OCV1OCV2规则
batchNo必填必填去首尾空格、转大写，最多 32 个字符，批次必须存在。
barcode必填必填去首尾空格、转大写，最多 32 个字符。
voltage必填必填有限数字，单位 V，不能静默修正。
internalResistance / resistance二选一二选一有限数字，单位 mΩ；统一转换为 internalResistance。
kValue不适用必填有限数字，单位 mV/h。
testTime必填必填带时区的 ISO 8601。
equipmentCode可选可选最多 64 个字符，缺失保存 NULL。
eventId可选可选最多 64 个字符；每条测量记录独立使用。

5.3 返回规则

单条成功继续返回当前电芯快照，避免影响现有设备客户端。批量成功时 data 保持为成功快照数组，meta 增加计数和失败明细。

{
  "success": true,
  "data": [
    { "barcode": "CELL001", "batchNo": "BATCH20260805", "ocv1Voltage": 3.685 }
  ],
  "message": "批量OCV1测试数据接收成功",
  "meta": {
    "accepted": 1,
    "duplicate": 0,
    "rejected": []
  }
}

批量存在失败记录时，已经保存的有效记录不回滚，接口返回 HTTP 400，并保留成功数据和失败明细：

{
  "success": false,
  "data": [
    { "barcode": "CELL001", "batchNo": "BATCH20260805", "ocv1Voltage": 3.685 }
  ],
  "message": "批量OCV1部分记录未接收",
  "error": {
    "code": "OCV_PARTIAL_FAILURE",
    "rejected": [
      {
        "index": 1,
        "barcode": "CELL002",
        "code": "OCV_STALE_TEST_TIME",
        "message": "测试时间早于当前快照"
      }
    ]
  },
  "meta": { "accepted": 1, "duplicate": 0, "rejected": 1 }
}

相同 eventId 且内容一致的重试返回 HTTP 200，并在 meta.duplicate 中计数；相同 ID 内容不同返回 HTTP 409。

  • 验证无 eventId 的重复上传每次新增历史；有相同 ID 的相同内容只处理一次；不同内容返回 409。
  • 验证批量部分失败时有效记录已经保存，HTTP 400 响应包含完整失败明细。
  • 验证旧的 NULL 条码 OCV 记录可读、不崩溃、不被错误关联到电芯。
  • 验证普通电芯追溯只返回快照，管理员审计接口支持分页和权限控制。
  • 使用真实 SQL Server 验证 migration、索引、锁竞争和大小写冲突；单元测试不能代替数据库集成测试。

Task 6：分阶段发布

  1. 备份数据库并记录所有目标表的行数、最大批次号长度、大小写冲突、旧 OCV NULL 条码行数和当前快照数量。
  2. 在预生产 SQL Server 执行 TypeORM migration，确认列元数据、索引和历史行数未异常变化。
  3. 先发布数据库结构，再发布 API；新字段保持兼容，使旧客户端在滚动发布期间仍能写入。
  4. 使用一批包含 32 位批次号、有效数据、缺失数据、迟到数据、重复事件和跨批次条码的测试报文进行验收。
  5. 确认设备在 HTTP 400 时只重试失败记录；如果设备不能按失败明细重试，不得直接上线部分成功模式。
  6. 检查 OCV 接口日志、审计记录、当前快照、批次统计和电芯追溯结果相互一致。
  7. 生产环境保持网络隔离，并设置请求体大小、连接超时和处理超时；批量业务上限为 1000 条。

7. 关键错误码

错误码场景是否写入
BATCH_NOT_FOUND批次不存在。该记录不写入。
OCV_VALIDATION_ERROR字段缺失、时间格式错误、数值非法或超过批量上限。该记录不写入。
CELL_BATCH_CONFLICT电芯已属于其他批次。原数据不变。
OCV_STALE_TEST_TIME设备测试时间早于当前快照。历史和快照都不写入。
OCV_EVENT_CONFLICT相同事件号对应不同测量内容。原事件不变。
OCV_PARTIAL_FAILURE批量中部分记录无效。有效记录保存，失败记录不保存。

8. 验收清单

  • OCV1、OCV2 单条和批量路径保持不变，旧设备客户端可以继续解析成功响应。
  • 批次号、电芯码、Pack 码新旧数据均按大写规则处理；历史大小写冲突不会被自动覆盖。
  • 批次号从数据库到 DTO、查询参数、前端类型和接口文档全链路支持 32 个字符。
  • OCV1 电压/内阻和 OCV2 电压/内阻/K 值缺失时拒绝记录。
  • 无效数值不会被夹紧、截断或替换为默认值。
  • 当前快照只接受时间不早于当前值的测量；相同时间以后接收的值可更新当前快照。
  • 每条有效上传都能通过条码、批次和 OCV 类型追溯到审计记录。
  • 无事件号的重复上传不丢数据；有事件号的重试不会产生重复记录。
  • 批量部分失败时有效记录可查、失败原因可查、设备可按失败明细重试。
  • 普通追溯展示当前值，管理员审计查询展示历史；两者职责不混淆。
  • OCV 流程顺序统一为分容、OCV1、OCV2、分选，且不阻断任何上传。
  • 旧 OCV 行没有条码时不会导致批次查询 JSON 解析失败，也不会错误归属到某个电芯。

9. 后续治理事项

下列规则已经在需求确认中确定，但不放入本次 OCV 接口交付，避免影响本次上线周期。
  • Pack 关联：保存未知电芯的待解析关系；同一时间一个电芯只能属于一个有效 Pack；释放旧关联需要操作人和原因；重组保留历史。
  • 分选接口：已有电芯跨批次上传时采用与 OCV 相同的拒绝规则；异常数值由夹紧改为拒绝并保留失败原因。
  • 人工工序：如果未来要求查询完整历史，再单独设计人工工序事件表，不把现有批次当前记录直接当历史表。
  • 公共接口安全：网络隔离稳定后再评估 API Key、签名校验和设备级权限。
